# 빈집진단서 디자인 일관성 검토

검토일: 2026-09-12 · 대상: 로컬 `http://127.0.0.1:3014` 및 현재 작업 폴더  
결과: **브랜드 방향은 일관되지만, 이전 전역 스타일과 새 화면별 스타일이 공존한다.**  
이 문서는 **수정 전 감사 시점의 기록**이다. 아래 수치·행 번호·스크린샷은 당시 기준으로 보존했다. 이후 사용자 승인으로 [디자인 시스템 v0.2](design-system.md)를 적용했으며, 현재 해결 여부는 [적용·검증 기록](design-system-implementation-2026-09-12.md)을 참고한다.

## 1. 전체 판단

유지할 요소는 크림색 지면, 짙은 녹색, 단순한 한 열 흐름, 비용 비교 카드, 선택에 따라 바뀌는 다음 행동, 대표 캐릭터 집토끼다. 진단서의 넓은 폭과 관리자의 정보 밀도는 화면 목적에 맞는 차이다.

우선 손볼 부분은 폰트 연결, 중요한 안내의 글자 크기, 입력 예시의 대비다. 그다음으로 같은 브랜드의 색상·제목·선택지·귀환 링크를 맞추면 된다. 전면적인 시각 재설계보다 기존 방향을 정리하는 작업을 권장한다.

**정리 항목 12건:** P1 3건, P2 7건, P3 2건. 이는 수정 우선순위이며 접근성 위반 건수나 제품 점수가 아니다. P1은 기기별 재현과 핵심 읽기, P2는 화면 간 일관성, P3는 유지보수·추가 사용성 개선이다.

검토 도구는 별도 Chrome/Playwright였다. 데스크톱 앱의 CUA 연결이 초기화 오류로 작동하지 않아 대체했다. 페이지 전환 중 일부 관리자 링크의 prefetch가 `net::ERR_ABORTED`로 남았지만, 주 문서 로딩·렌더링 실패는 관찰하지 않았다. 주요 네트워크 요청 전체가 오류 0이었다고 주장하지 않는다.

## 3. 불일치와 개선 항목

### DS-01 · P1 · 불러온 웹폰트와 사용하는 폰트 이름이 다름

**근거:** [layout.tsx](../app/layout.tsx) 17~25행, [globals.css](../app/globals.css) 24~25행.

`Pretendard Variable` CSS를 로드하지만 `--font-sans`는 `Pretendard`를 지정한다. 현재 Mac에서는 설치된 Pretendard가 사용되어 문제가 가려진다. `isCustomFont:false`와 미사용 웹폰트를 확인했다. 검토용 브라우저의 변수만 올바르게 바꾸자 `Pretendard Variable`, `isCustomFont:true`로 전환됐다.

**영향:** 폰트가 없는 기기에서는 대체 글꼴로 표시될 수 있어 굵기·글자 폭·줄바꿈이 달라진다. 정적 폰트에서는 650·730·750 같은 중간 굵기도 의도대로 재현되지 않을 수 있다.

**권장:** 가족 이름 일치 → 웹폰트 사용 확인 → 글자 크기와 배치 재측정 순서로 수정. [실험 원자료](../output/design-audit-2026-09-12/targeted-checks.json)

### DS-02 · P1 · 중요한 설명과 조작 글자가 작고 크기 규칙이 흩어짐

**근거:** [home.module.css](../app/home.module.css) 45~51, 65~80, 114~118, 165~170행; [support-cards.module.css](../app/report/support-cards.module.css) 13~22행; [admin.module.css](../app/admin/admin.module.css) 24~26행.

- 홈의 개인정보 안내 12px, 미확인 표식 모바일 10px, 예시 안내 10px, 푸터 링크 11px.
- 지원 카드의 확인/미확인 작은 표식은 10px. 펼친 상태에서 읽을 설명은 주로 13px.
- 관리자 검색 입력·필터는 상위 라벨에서 13px을 상속한다. 상세 select/textarea는 14px이다.
- 홈 본문 기준 15px, 보고서 16px, 전역 16/17px이 섞여 있다.

**권장:** 고객용 본문 16px, 보조 설명 14px, 작은 표식 12px. 금액이나 지원 여부를 판단하는 핵심 제약은 작은 표식에만 넣지 않는다. 입력은 관리자를 포함해 16px 권장. 이 제안은 독자와 정보 중요도를 고려한 기준이며 단순히 12px 미만이면 WCAG 위반이라는 뜻은 아니다.

### DS-03 · P1 · 홈 주소 입력 예시의 대비 부족

**근거:** [home.module.css](../app/home.module.css) 57행. 실제 placeholder의 색 `rgb(127,135,123)`, opacity 1, 배경 흰색을 확인했다.

`#7F877B` / `#FFFFFF`의 대비는 **3.714:1**이다. 일반 텍스트와 placeholder에 적용되는 4.5:1 기준에 미달한다. [W3C 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**권장:** 보조 본문색 `#5C6D62`처럼 더 짙게 변경하고 다른 필드의 placeholder도 확인. [측정값](../output/design-audit-2026-09-12/contrast-samples.json)

### DS-04 · P2 · 팔레트와 토큰이 세 체계로 갈라짐

**근거:** [globals.css](../app/globals.css) 4~22행, [home.module.css](../app/home.module.css) 1~4행, [report.module.css](../app/report/report.module.css) 1행, [admin.module.css](../app/admin/admin.module.css) 2~4행.

주요 녹색 `#0F5347` / `#285C49`, 지면 `#FBFBF9` / `#FFFEFA`, 본문 `#16302C` / `#263D34`가 같은 역할로 사용된다. 공식 정보·사진·조회 모듈은 색 직접 지정도 많다. 현재 같은 집 로고 옆 이름의 색도 홈과 관리자가 다르다.

**권장:** 최신 홈/보고서의 팔레트를 의미별 공통 토큰으로 통합. 관리자 배경·정보 밀도는 변형으로 남기되 브랜드 색은 공유. 색이 다르다는 이유로 확인/오류/대기처럼 다른 의미의 색까지 합치지 않는다.

### DS-05 · P2 · 제목의 계층과 글꼴이 화면별로 달라짐

**근거:** [home.module.css](../app/home.module.css) 10~12, 26행; [report.module.css](../app/report/report.module.css) 16, 25행; [privacy/page.tsx](../app/privacy/page.tsx)의 H1/H2.

데스크톱 홈은 H1·H2 모두 29px인데 지원정보 H1은 36px이다. 모바일 홈 H1은 25px, 조회/신청/지원정보는 29px이다. 개인정보 화면은 Noto Serif KR 명조와 18px 섹션 제목을 쓴다. 관리자 로그인 제목 굵기는 600, 목록은 750이다.

**권장:** 페이지 제목·섹션 제목·카드 제목 역할을 정하고 별도 변형의 이유를 기록. 기본 32/28, 24/22, 20/18px을 검토하되 웹폰트 수정 이후 긴 한국어 제목이 과도하게 줄바꿈되지 않는지 다시 본다.

### DS-06 · P2 · 추가 신청 폼의 시각 언어와 선택 표시가 다름

**근거:** [home.module.css](../app/home.module.css) 125행, [apply-form.tsx](../app/apply-form.tsx) 36~41, 61~88행, [photo-picker.module.css](../app/photo-picker.module.css).

홈·조회는 밝은 배경의 선택 카드이며 선택 시 카드의 테두리/배경이 바뀐다. 신청 폼은 넓은 짙은 녹색 배경, 청록색 카드, 6px 둥글기다. 신청 폼에서 ‘상속’ 선택 전후를 비교하면 카드의 색과 경계는 같고 라디오 점만 바뀐다. 오작동은 아니지만 선택을 빠르게 구분하기 어렵다.

**권장:** 밝은 고객용 폼으로 맞추거나 inverse 변형을 명시. 두 경우 모두 선택된 label의 면·선도 변경. 사진 선택기는 어두운 테마 전용이므로 폼 테마를 바꾸면 같이 조정해야 한다. [신청 화면](../output/design-audit-2026-09-12/apply-375.png)

### DS-07 · P2 · 헤더 브랜드·뒤로가기·푸터가 일관되지 않음

**근거:** [home-ui.tsx](../app/home-ui.tsx) 20~33행, [report.module.css](../app/report/report.module.css) 6~10행과 모바일 규칙, [apply/page.tsx](../app/apply/page.tsx), [privacy/page.tsx](../app/privacy/page.tsx).

모바일 브랜드 글자는 홈 18px, 진단서 16px, 관리자 17px이다. 아이콘은 모두 40px으로 공유한다. 홈으로 돌아가는 표현도 `홈으로`, `← 처음으로`, `빈집진단서로 돌아가기`로 다르며 개인정보는 하단까지 내려가야 귀환 링크를 만난다. 일부 고객 푸터는 10~11px이다.

**권장:** 공통 Brand와 HomeLink 사용. 고객용 하위 화면에 상단 `← 홈으로` 제공. 관리자 ‘목록으로’는 다른 목적이라 별도 유지. 브랜드 글자는 20/18px 변형으로 통일하는 것을 권장한다.

### DS-08 · P2 · ‘미확인’의 시각 규칙이 컴포넌트마다 다름

**근거:** [globals.css](../app/globals.css) 50~53행, [home.module.css](../app/home.module.css) 76~79행, [report.module.css](../app/report/report.module.css)의 `.unverified`, [support-cards.module.css](../app/report/support-cards.module.css) 7, 15~17행.

전역 규칙은 점선, 홈은 황갈색 바탕+점선, 보고서 근거의 ‘추가 확인 필요’는 점선 없는 11px 표식, 지원 카드의 미확인은 10px+점선이다. 관리자 ‘고객 확인 대기’ 역시 점선을 쓰지만 이는 집의 정보 확인 여부와 다른 개념이다.

**권장:** 정보 상태용 Badge와 업무 상태용 Badge를 분리하고, 같은 정보 상태 안에서 크기·색·선·문구를 공유. 텍스트가 이미 있으므로 색만으로 상태를 전달하는 문제로 확대 해석하지 않는다.

### DS-09 · P2 · 600px 화면에서 같은 진단서의 제목 크기가 어긋남

**근거:** [report.module.css](../app/report/report.module.css)의 620px 미디어쿼리, [support-cards.module.css](../app/report/support-cards.module.css) 27행의 540px 쿼리.

600px 실제 화면에서 일반 섹션 제목은 22px인데 ‘우리 집도 지원을 받을 수 있을까요?’는 24px이다. 서로 다른 모듈의 전환점 때문에 중간 폭에서 위계가 역전된다.

**권장:** 같은 보고서에 속한 제목의 반응형 기준을 공유. 모든 페이지의 모든 전환점을 무조건 하나로 합칠 필요는 없다. [재현 결과](../output/design-audit-2026-09-12/breakpoint-600.json)

### DS-10 · P2 · 인쇄의 최소 글자 규칙이 실제 결과에 적용되지 않음

**근거:** [globals.css](../app/globals.css) 85~86행, [report.module.css](../app/report/report.module.css)의 개별 px 글자와 print 규칙.

전역 주석은 ‘인쇄 최소 12pt’인데 print 미디어에서도 보고서의 메타·도움말·표 항목에는 11~15px가 남는다. 12pt는 CSS 기준 16px에 해당하므로 body만 지정해서는 의도를 만족하지 못한다. [단위 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**권장:** 읽을 내용의 print용 크기를 별도로 지정하고, 표·카드가 페이지에서 잘리지 않는지 확인. 현재 인쇄 버튼·입력기 등은 숨겨지는 것을 확인했지만 내부 이동용 링크 일부는 남아 있으므로 출력 목적에 맞게 정리한다. 페이지 나눔 완전성은 이번 검토에서 판정하지 않았다.

### DS-11 · P3 · 둥글기·여백이 요소별 값으로 늘어남

**근거:** [CSS 집계](../output/design-audit-2026-09-12/source-clean-counts.json). 단일 px 둥글기만 4·5·6·7·8·9·10·12·13·14·16·20·22·24·30의 15종이다. 원형·부분 둥글기·Tailwind 클래스 값은 이 집계에서 제외했다.

주소 입력은 홈 13px, 조회 9px, 신청 6px, 계산기 6px, 관리자 8px이다. 화면 간 역할이 비슷해도 서로 다른 값을 갖는다. 카드 안쪽 22·23·24px과 섹션 안쪽 36·40·42·43px도 혼재한다.

**권장:** 역할 기반 둥글기 6/8/12/16/20과 간격 규모를 정의. 서류 탭·원형 번호·캐릭터 위치 등 분명한 시각 목적이 있는 예외는 유지.

### DS-12 · P3 · 모바일 홈의 설명 영역이 좁고 입력 도달까지 김

**근거:** [홈 375px 상단](../output/design-audit-2026-09-12/home-top-375.png). 소개 문장은 토끼 옆 약 189px 영역에서 ‘단독주/택’, ‘돕/는’처럼 끊긴다. 같은 화면에서 주소 입력 위쪽은 약 y=641px, 조회 버튼은 약 y=865px이다.

이는 가로 넘침이나 토끼의 잘림이 아니라 읽기와 시작 동선의 개선 후보다. 소개 다음에 비슷한 메시지를 다시 보여주며 입력 시작이 길어진다. 실제 이탈이 발생했다는 데이터는 없다.

**권장:** 현재 집토끼 크기·위치를 보존하면서 설명문을 아래 전폭 행으로 분리하고 중복 소개를 줄이는 안을 검토. 단어 단위 줄바꿈도 함께 적용. 전환율 개선을 보장하지 말고 첫 입력까지 걸린 시간과 과업 완료를 관찰한다.

## 4. 의도적으로 달라도 되는 부분

- 홈 704px, 보고서 940px, 관리자 1208px: 읽기·비교·업무의 역할 차이로 설명 가능하다.
- 홈·보고서·관리자 집토끼의 크기: 역할과 기존 사용자 조정이 있어 동일 크기로 강제하지 않는다.
- 제목/금액/카드명: 의미별로 다른 크기가 필요하다. 역할이 같은 요소의 규칙을 통일한다.
- 기관 링크와 앱 내부 버튼: 외부 이동·새 창 여부를 명확히 표현할 수 있다.
- 관리자 상태와 집의 확인 상태: 개념이 달라 상태 색/문구까지 하나로 합치지 않는다.

## 5. 권장 실행 순서

**첫 묶음:** DS-01 폰트 → DS-02 핵심 글자 → DS-03 입력 예시 대비. 폰트 수정은 줄바꿈에 영향을 주므로 가장 먼저 한다.

**두 번째 묶음:** DS-04 색 토큰 → DS-05 제목 역할 → DS-07 브랜드/귀환 → DS-08 상태. 공통 컴포넌트로 묶으면서 일관성을 확보한다.

**세 번째 묶음:** DS-06 신청 폼 → DS-09 반응형 → DS-10 인쇄. 신청 테마 결정은 사진 선택기·성공/오류 상태까지 함께 확인한다.

**마지막 묶음:** DS-11 값 정리와 DS-12 모바일 소개 구성. 새 값이 실제 읽기와 과업 완료를 개선하는지 검토한다.

이번에 생성한 것은 문서와 검토 증거뿐이다. 사이트 수정·의존성 설치·커밋·배포·실제 신청 제출은 하지 않았다. 실행 기준은 [디자인 시스템](design-system.md)을 따른다.
